# 第 4 篇：Electron 图标制作、替换与打包

先回答最容易混淆的问题：**改了托盘图标，不等于改了应用图标；改了页面 favicon，也不等于改了 Electron 安装包图标。** 这些图标出现在不同位置，由不同文件和配置控制。

本篇先盘点 jyt-pocket 实际已经替换的图标，再提供完整替换步骤。命令块是学习操作示例，本教程没有自动修改应用图标或执行打包。

## 1. 第一步：识别四类图标

| 类型 | 用户在哪里看到 | 控制位置 |
| --- | --- | --- |
| 应用图标 | Finder 的 `.app`、Windows 可执行文件与快捷方式、系统启动器 | electron-builder 的平台 icon 配置 |
| 窗口图标 | Windows/Linux 窗口相关 UI | `BrowserWindow({ icon })`，平台支持有差异 |
| 托盘图标 | macOS 顶部状态栏、Windows/Linux 系统托盘 | `new Tray(image)` |
| 网页 favicon | 浏览器预览标签页等网页环境 | HTML 的 `<link rel="icon">` |

另外还有页面里的品牌标识，例如侧边栏的 Lucide `Terminal` 组件。它只是一段页面 UI，不决定操作系统认出的应用图标。

即使项目隐藏了 Dock，也应该制作正式应用图标：Finder、安装包、系统搜索、快捷方式仍可能展示它。

## 2. 当前项目的图标到底改了哪些

以下是编写教程时读取本地文件得到的结果：

| 文件 | 尺寸或格式 | 当前用途与状态 |
| --- | --- | --- |
| `resources/trayTemplate.png` | 22 × 22 PNG | 已新增，macOS 普通倍率托盘模板图 |
| `resources/trayTemplate@2x.png` | 44 × 44 PNG | 已新增，macOS Retina 模板图 |
| `resources/tray.png` | 32 × 32 PNG | 已新增，其他平台彩色托盘图 |
| `resources/tray.svg` | SVG | 终端形状的矢量源，便于后续导出 |
| `src/renderer/public/pocket.svg` | `viewBox` 为 40 × 40 | 已有自定义网页 favicon |
| `resources/icon.png` | 512 × 512 PNG | 仍为模板图，主入口仅在 Linux 传给窗口 |
| `build/icon.png` | 512 × 512 PNG | 仍为模板应用资源 |
| `build/icon.ico` | ICO | 仍为模板 Windows 应用资源 |
| `build/icon.icns` | ICNS | 仍为模板 macOS 应用资源 |

SVG 的 `viewBox` 定义坐标系统，不等于位图只有 40 个物理像素。PNG 的 22 × 22 则确实表示位图像素数量。

因此，当前已经实现的是自定义托盘入口；正式打包应用图标还需要按后面的步骤替换。

## 3. 第二步：理解 PNG、SVG、ICO、ICNS

| 格式 | 特点 | 适合哪里 |
| --- | --- | --- |
| SVG | 矢量，可按目标尺寸重新渲染 | 设计源、网页图标、构建工具的输入 |
| PNG | 位图，支持透明通道 | 托盘、Linux 应用图标、通用设计导出 |
| ICO | 可包含多个尺寸的图像 | Windows 应用与快捷方式图标 |
| ICNS | macOS 应用图标容器，包含不同尺寸表示 | macOS `.app` |

把 `logo.png` 重命名成 `logo.ico` 不会转换格式。扩展名只是名字，文件内部编码没有变。

`nativeImage` 的跨平台稳妥输入是 PNG 等受支持位图；不能因为浏览器能显示 SVG，就假设 `new Tray('某个.svg')` 在每个平台都能工作。当前项目在运行时使用 PNG，SVG 只作为源文件。

electron-builder 构建时对源图的转换能力，与 Electron 运行时 `nativeImage` 支持的格式是两件事。即使构建工具可以吃 SVG，也不能据此推导 Tray 支持 SVG。

## 4. 第三步：图标到底做多大

### 4.1 应用图标

推荐保留一份 **1024 × 1024 的高质量透明 PNG 或矢量母稿**，再导出各平台需要的尺寸，不要从 32 × 32 托盘图强行放大。

| 目标 | 本教程采用的准备方案 |
| --- | --- |
| macOS 应用 | 由 1024 母稿生成多尺寸 `icon.icns` |
| Windows 应用 | 准备真正的多尺寸 `icon.ico`，或使用 builder 支持的 PNG 转换 |
| Linux 应用 | 至少准备清晰的 512 × 512 PNG；可另外提供多尺寸集合 |
| 窗口图标 | 可复用应用图形，但小尺寸显示仍需清晰 |
| 网页 favicon | SVG，或按需要提供 16/32 等尺寸 PNG |

这里给的是项目实践方案，不是说每个平台只支持这一个尺寸。正式图标最好保留不同尺寸下的视觉优化，尤其细线图形缩到 16 像素时可能需要加粗或减少细节。

### 4.2 托盘与 macOS 菜单栏图标

Electron 的 Tray 文档给出的常见 macOS 基线是 16 × 16 的 1 倍图和 32 × 32 的 2 倍图。实际设计也常围绕 18 或 22 的画布调整留白；本项目实际使用 **22 × 22 与 44 × 44**，并不意味着所有应用都必须使用 22。

托盘图案应简单、轮廓明确、留有透明边距。不要把完整品牌文字、细小装饰塞进去，也不要因为画布有 22 像素就把每个像素都画满。

Windows 托盘可以使用 PNG，但多尺寸 ICO 更便于覆盖不同系统缩放。当前项目为 Windows/Linux 使用 32 × 32 PNG，属于现有实现；后续可以增加专门的 Windows ICO。

### 4.3 逻辑尺寸与 @2x

假设一个托盘图标希望以 22 个逻辑单位显示：

```text
普通倍率：22 逻辑单位 × 1 = 22 物理像素
Retina：  22 逻辑单位 × 2 = 44 物理像素
```

`@2x` 表示相同逻辑尺寸下提供更多像素，不是希望它显示成两倍大的图标。

不要给 22 像素图重复声明 `scaleFactor: 2` 冒充高清图。应该真的准备 44 像素位图。

对于 PNG，先保证像素尺寸、透明通道与 scaleFactor 对应；仅修改文件的 DPI 标记，不能补出缺失的图像细节。

## 5. 第四步：制作 macOS Template 图标

Template 在这里表示“交给系统着色的模板图”，与“Electron 工程模板的默认图标”不是同一个概念。

准备要求：

1. 透明背景。
2. 用黑色及透明度表达图形轮廓。
3. 不把背景绘制成白色方块。
4. 分别导出 1 倍和 2 倍位图。
5. 在代码中标记为模板图像。

系统根据菜单栏背景和显示状态调整颜色，应用不需要自己监听明暗模式后手动换黑白两张图。

当前项目的加载代码在主进程：

```ts
import { nativeImage, Tray } from 'electron'
import { readFileSync } from 'node:fs'
import trayIcon from '../../resources/trayTemplate.png?asset'
import trayIcon2x from '../../resources/trayTemplate@2x.png?asset'
import trayColorIcon from '../../resources/tray.png?asset'

const image = nativeImage.createFromPath(
  process.platform === 'darwin' ? trayIcon : trayColorIcon
)

if (process.platform === 'darwin') {
  // 同一逻辑图标添加 Retina 位图表示。
  image.addRepresentation({
    scaleFactor: 2,
    buffer: readFileSync(trayIcon2x)
  })
  image.setTemplateImage(true)
}

if (image.isEmpty()) {
  throw new Error('菜单栏图标加载失败，请重新安装应用')
}

const tray = new Tray(image)
```

每个 API 的作用：

| API | 解决的问题 |
| --- | --- |
| `createFromPath()` | 从资源文件创建 NativeImage |
| `addRepresentation()` | 为同一逻辑图标补充高倍率图像 |
| `scaleFactor: 2` | 告诉 Electron 这是 2 倍像素密度 |
| `setTemplateImage(true)` | 在 macOS 中使用系统模板着色 |
| `isEmpty()` | 及时发现路径错误或图像加载失败 |
| `new Tray(image)` | 在系统托盘或状态栏创建入口 |

### 5.1 为什么手动 addRepresentation

Electron 支持按 `@2x` 等命名约定寻找高倍率资源。但构建工具可能改写资源文件名，不能只假设打包后名字还满足自动关联规则。

项目把两张图都通过 `?asset` 导入，再显式添加高倍率表示，避免依赖构建后文件名的隐含关系。

### 5.2 为什么其他平台用彩色图

macOS 模板着色是特定平台机制。当前项目给其他平台准备有底色的终端图，确保在不同托盘背景上仍可辨认，不把 macOS 的黑色轮廓方案直接照搬到所有桌面环境。

## 6. 第五步：替换托盘图标

这是与当前代码直接对应的操作流程：

1. 在设计工具中编辑原始矢量图形，保持简洁轮廓与透明边距。
2. 导出黑色透明的 `trayTemplate.png`，22 × 22。
3. 从同一矢量母稿导出 `trayTemplate@2x.png`，44 × 44。
4. 导出其他平台使用的 `tray.png`，32 × 32。
5. 覆盖项目 `resources/` 下对应文件。
6. 重启 Electron 主进程，观察实际系统托盘。

只刷新 React 页面通常不会重新创建主进程已经持有的 Tray 图像。开发中改完图片没变化，先分清刷新的是页面还是整个 Electron 进程。

在应用运行过程中动态换图，使用：

```ts
const nextImage = nativeImage.createFromPath(nextIconPath)
if (!nextImage.isEmpty()) tray.setImage(nextImage)
```

`nextIconPath` 应是已知资源路径。这是可用 API 示例，当前项目没有实现运行时图标编辑器。

## 7. 第六步：生成正式 macOS 应用图标

下面是一套可以照着执行的 macOS 命令。前提是你已准备真正的 **1024 × 1024** 母稿，放到项目的：

```text
resources/app-icon-1024.png
```

这个文件名是教程建议的新素材，不是当前项目已经存在的文件。

先生成 iconset。以下命令在项目根目录执行，使用 macOS 自带的 `sips`：

```sh
mkdir -p build/app.iconset

# 从母稿生成普通倍率和 Retina 倍率，不从小图反复放大。
for icon_size in 16 32 128 256 512; do
  sips -z "$icon_size" "$icon_size" resources/app-icon-1024.png \
    --out "build/app.iconset/icon_${icon_size}x${icon_size}.png"

  retina_size=$((icon_size * 2))
  sips -z "$retina_size" "$retina_size" resources/app-icon-1024.png \
    --out "build/app.iconset/icon_${icon_size}x${icon_size}@2x.png"
done
```

得到的命名包括：

```text
icon_16x16.png          实际 16 × 16
icon_16x16@2x.png       实际 32 × 32
icon_32x32.png          实际 32 × 32
icon_32x32@2x.png       实际 64 × 64
icon_128x128.png        实际 128 × 128
icon_128x128@2x.png     实际 256 × 256
icon_256x256.png        实际 256 × 256
icon_256x256@2x.png     实际 512 × 512
icon_512x512.png        实际 512 × 512
icon_512x512@2x.png     实际 1024 × 1024
```

再用 macOS 自带的 `iconutil` 生成真正的 ICNS 文件：

```sh
iconutil -c icns build/app.iconset -o build/icon.icns
```

这一步会替换正式应用图标文件，应该在确定新母稿后执行。不要拿 Tray 的 Template 黑色图直接当应用图标，应用图标和状态栏图标可以共享图形语言，但有不同的显示场景。

## 8. 第七步：准备 Windows 与 Linux 图标

### 8.1 Windows 多尺寸 ICO

使用能导出多尺寸 ICO 的图标工具，从母稿生成 `build/icon.ico`。可以包含 16、20、24、32、40、48、64、256 等尺寸，以覆盖常见系统缩放与图标展示位置。

重点是检查 ICO 内部确实包含多个尺寸，并不是在扩展名或文件名里写了“256”。小尺寸最好单独检查细线与留白。

electron-builder 也支持从符合要求的 PNG 自动转换。若采用此方案，可以显式指定 PNG 输入：

```yaml
# 替代方案：与下一节的 win.icon: build/icon.ico 二选一。
win:
  icon: build/icon.png
```

使用足够清晰的 512 或 1024 像素方形 PNG，并以项目实际安装的 builder 版本文档为准。显式指定路径，避免继续选中旧的模板 ICO。

### 8.2 Linux PNG 与运行时图标

在 macOS 上也可以先导出 PNG：

```sh
sips -z 512 512 resources/app-icon-1024.png --out build/icon.png
cp build/icon.png resources/icon.png
```

两份文件承担不同职责：`build/icon.png` 给打包工具，`resources/icon.png` 给当前主进程窗口加载。替换其中一个，不代表另一个同步改变。

更完整的 Linux 图标集合可以放在独立目录，按 builder 文档要求命名为 `16x16.png`、`32x32.png`、`256x256.png` 等，再把 `linux.icon` 指向该目录。当前教程先采用单张 512 PNG 的直接方案。

## 9. 第八步：明确 electron-builder 图标配置

这是**建议配置片段**，需要合并到项目已有 YAML 的相应节点，不要在文件末尾重复增加第二个 `mac`、`win`、`linux` 节点：

```yaml
appId: com.jyt.pocket
productName: jyt-pocket

directories:
  buildResources: build

mac:
  icon: build/icon.icns
  extendInfo:
    LSUIElement: true

win:
  executableName: jyt-pocket
  icon: build/icon.ico

linux:
  icon: build/icon.png
```

保留原来的 entitlements、产物名称、Linux target 等设置，只修改相关字段。

当前 builder 配置已经使用 `buildResources: build`，所以默认命名的图标也能参与构建；显式写路径的好处是读代码就知道各平台用了哪份素材。

当前还有一处值得后续统一：主进程使用的 Windows 标识是 `com.jyt.pocket`，而 `electron-builder.yml` 的 `appId` 仍是模板 `com.electron.app`。上面的示例给出统一后的建议，教程没有替你修改现有工程。

`buildResources` 是构建工具资源目录，不表示任意文件都会作为运行时资源暴露给主进程。运行时用到的图片仍要通过明确资源导入或打包配置保留。

## 10. 第九步：替换窗口图标与网页图标

### 10.1 窗口图标

当前主入口：

```ts
import icon from '../../resources/icon.png?asset'

const mainWindow = new BrowserWindow({
  // 其他窗口参数省略。
  ...(process.platform === 'linux' ? { icon } : {})
})
```

这是项目**目前只在 Linux 设置**窗口图标的写法。需要调整 Windows 运行时窗口图标时，可按目标平台选择 ICO 或受支持图像；它仍不等于修改 Windows 安装包内嵌图标。

macOS 的正式应用图标应通过 `.app` 的图标资源与打包配置处理。不要期待 `BrowserWindow({ icon })` 替换 Finder 的 `.app` 图标。

macOS 开发时若需要临时看 Dock 图标，可使用：

```ts
// 仅供理解运行时 Dock API；当前项目主动隐藏 Dock，因此通常看不到它。
app.dock?.setIcon(nativeImage.createFromPath(appIconPath))
```

它不修改磁盘上的 `.app` 图标资源，也不代替正式 ICNS 打包。

### 10.2 网页 favicon

前端 HTML 使用：

```html
<link rel="icon" type="image/svg+xml" href="/pocket.svg" />
```

资源位于 `src/renderer/public/pocket.svg`，由 renderer 的构建流程处理。它主要影响网页环境，不能决定托盘、Finder 或 EXE 的图标。

侧边栏 Lucide 图标则在 React 组件里替换，是另一处 UI 代码。

## 11. 第十步：开发、编译、打包分别验证什么

| 操作 | 项目命令 | 能观察什么 |
| --- | --- | --- |
| 开发 | `npm run dev` | 页面、窗口、托盘与主进程行为 |
| 编译 | `npm run build` | 类型检查及 main/preload/renderer 编译产物 |
| 解包应用 | `npm run build:unpack` | 可运行应用目录，适合检查实际打包资源 |
| macOS 包 | `npm run build:mac` | 当前平台的 `.app`、磁盘镜像等构建结果 |
| Windows 包 | `npm run build:win` | Windows 目标产物，需对应构建环境支持 |
| Linux 包 | `npm run build:linux` | 配置的 AppImage、snap、deb 等目标 |

以上是项目 `package.json` 中已有脚本，不代表本教程执行了这些命令。尤其跨平台构建、签名和目标格式对宿主环境有要求，不能承诺任意系统上都能一条命令完成全部平台。

当前 `build:mac`、`build:linux` 直接执行 electron-vite 构建，没有包含与 `build` 脚本相同的显式 typecheck。准备发布时应了解脚本实际内容，不能只看命令名称猜验证范围。

开发时实际启动的是依赖中的 Electron 可执行程序，某些系统位置仍会显示 Electron 默认身份。正式应用图标要检查**重新生成的打包产物**，不能只盯着开发进程判断替换失败。

### 11.1 asar 是什么

electron-builder 通常把应用代码与资源整理进 `app.asar`，它是应用资源归档，不是加密，也不是用户数据目录。

项目有：

```yaml
asarUnpack:
  - resources/**
```

这让匹配的资源保留为解包文件。图片通过 `?asset` 引用时，要检查构建后的实际资源布局；不能把开发时的相对路径直接硬编码到打包程序中。

### 11.2 图标正确不等于可正式分发

当前配置还有模板信息，例如作者、更新地址；macOS 配置中 `notarize: false`。所以教程中的“打包完成”只表示生成产物，不能表述成已经完成可信签名、公证或自动更新部署。

正式分发还要按平台准备签名、公证及真实发布配置，这是独立工作。隐藏 Dock 的 `LSUIElement` 与签名、公证也没有替代关系。

## 12. 常见问题排查

| 现象 | 优先检查 |
| --- | --- |
| 托盘里是一块黑色或白色方块 | PNG 背景是否透明；Template 图是否把整块背景画实 |
| Retina 屏幕图标发糊 | 是否真的提供 2 倍图；`scaleFactor` 与像素尺寸是否对应 |
| 明暗菜单栏下看不清 | macOS 是否 `setTemplateImage(true)`；图形是否适合模板着色 |
| 改了图片但托盘没变 | 是否只热更新页面，主进程仍持有旧 NativeImage |
| 打包后图标消失 | `?asset` 导入路径、构建资源、`isEmpty()` 错误提示 |
| favicon 变了但应用还是 Electron 图标 | 改错图标类别，需要处理 builder 的应用图标 |
| macOS Finder 还是旧图标 | 是否运行旧 `.app`；是否重新打包；系统是否仍缓存旧显示 |
| Windows 任务栏仍显示默认图标 | 是否使用旧安装包/快捷方式；EXE 图标与运行时窗口图标分别核对 |
| 隐藏 Dock 后找不到应用 | Tray 是否创建成功，全局快捷键是否注册成功 |
| Linux 托盘显示与 macOS 不同 | 桌面环境的托盘实现与支持情况 |

图标缓存问题先通过退出旧应用、确认新产物路径、重新安装等常规方式排查。不要一开始就删除系统缓存或执行不清楚用途的系统命令。

## 13. 素材来源与许可证

当前托盘矢量源采用 Lucide Terminal 图形，项目资源文件保留了相关来源/许可说明。后续替换图标时也应记录来源。

程序里能引用一张图片，不等于获得了重新分发它的权利。自用素材和开源安装包里的素材都应使用自己创作或授权允许的内容。这里只需要保留明确来源与许可证，不必为普通图标引入复杂机制。
