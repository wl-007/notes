# 第 3 篇：IPC、命令执行、日志与本地数据

前两篇的窗口和托盘都在主进程中完成。本篇解决另一个核心问题：React 页面怎样安全地使用这些能力？

## 1. 第一步：理解 IPC 是什么

IPC 是进程间通信。页面要选文件、执行命令时，不能直接取得主进程对象；它发送请求，由主进程检查参数、执行操作、返回结果。

本项目主要使用两种模式：

| 模式 | 请求或发送端 | 接收端 | 适合什么 |
| --- | --- | --- | --- |
| 请求与响应 | `ipcRenderer.invoke()` | `ipcMain.handle()` | 保存数据、选目录、启动执行 |
| 持续推送 | `webContents.send()` | `ipcRenderer.on()` | stdout/stderr 日志、窗口动作 |

`invoke()` 返回一个 Promise，适合一次操作的一次结果。日志可能连续产生很多次，不能只靠最初请求的返回值，因此另设推送通道。

通道名如 `pocket:load` 是项目自定字符串，不是 Electron 预设名字；双方写法必须一致。

## 2. 第二步：用“隐藏窗口”走通最小 IPC

下面是独立教学版本。它展示三处代码的对应关系；本项目真实接口增加了统一 `Result` 封装，见下一节。

### 2.1 主进程注册处理器

```ts
import { ipcMain, type BrowserWindow } from 'electron'

function registerWindowIPC(mainWindow: BrowserWindow): void {
  ipcMain.handle('demo:hide-window', (event): void => {
    // 只接受指定窗口主页面发出的请求。
    if (
      event.sender !== mainWindow.webContents ||
      event.senderFrame !== mainWindow.webContents.mainFrame
    ) {
      throw new Error('不受信任的请求来源')
    }

    mainWindow.hide()
  })
}
```

创建窗口后调用一次 `registerWindowIPC(mainWindow)`。同一个 channel 不能随意重复注册多个 handler。

### 2.2 preload 暴露固定方法

```ts
import { contextBridge, ipcRenderer } from 'electron'

const demoAPI = {
  hideWindow: (): Promise<void> => ipcRenderer.invoke('demo:hide-window')
}

contextBridge.exposeInMainWorld('demoAPI', demoAPI)
```

### 2.3 页面声明类型并调用

```ts
// 渲染进程的 .d.ts 文件。
export {}

declare global {
  interface Window {
    demoAPI: {
      hideWindow: () => Promise<void>
    }
  }
}
```

```ts
// 页面事件回调中。
await window.demoAPI.hideWindow()
```

`contextBridge.exposeInMainWorld('demoAPI', ...)` 决定页面看到的名字。TS 声明只是告诉编辑器类型，不会凭空创建这个运行时对象。

不要暴露 `ipcRenderer` 整个对象，也不要暴露一个允许页面任意传 channel 的万能 `send()`。固定业务方法更容易审查每个入口的权限和参数。

## 3. 第三步：项目怎样统一成功与失败

项目在 `src/shared/types.ts` 定义：

```ts
export type Result<T> =
  | { ok: true; data: T }
  | { ok: false; error: string }
```

对应的 API 类型节选：

```ts
export interface PocketAPI {
  hideWindow: () => Promise<Result<void>>
  windowReady: () => Promise<Result<void>>
  executeCommand: (commandId: string, cwd: string) => Promise<Result<string>>
  setAlwaysOnTop: (value: boolean) => Promise<Result<void>>
  // 其余业务方法见项目 types.ts。
}
```

页面通过判别字段缩小类型：

```ts
const result = await window.api.hideWindow()
if (!result.ok) {
  throw new Error(result.error)
}
```

项目有 `unwrap()` 辅助函数做相同处理，再由界面统一显示 toast。即使使用业务 `Result`，通信通道断开等仍可能使 Promise reject，因此调用方仍要捕获异常。

### 3.1 主进程的 handle 是项目自己的包装

`src/main/ipc.ts` 的关键结构如下：

```ts
const handle = (
  channel: string,
  callback: (...args: unknown[]) => Promise<unknown> | unknown
): void => {
  ipcMain.removeHandler(channel)
  ipcMain.handle(channel, async (event, ...args: unknown[]): Promise<Result<unknown>> => {
    try {
      if (
        event.sender !== window.webContents ||
        event.senderFrame !== window.webContents.mainFrame
      ) {
        throw new Error('不受信任的请求来源')
      }

      return { ok: true, data: await callback(...args) }
    } catch (error) {
      return {
        ok: false,
        error: error instanceof Error ? error.message : '操作失败，请重试'
      }
    }
  })
}

handle('pocket:hide-window', () => window.hide())
```

这里原生 API 是 `ipcMain.handle()`。短名字 `handle()` 是我们为了复用来源校验和错误处理写的封装；`removeHandler()` 让当前单窗口应用重新注册时不重复占用通道。多窗口应用需要重新设计归属，不能让后一个窗口无条件覆盖前一个窗口的处理器。

入口参数先用 `unknown`，表示还没验证。不是把 TS 类型写成 `CommandItem` 就能保证对方传来的数据正确。

来源校验能拒绝其他窗口或 iframe 的请求，但不能保证当前主页面绝不被 XSS 控制。因此窄接口、参数校验、命令限制、页面加载边界仍然有必要。

## 4. 第四步：主进程怎样推送消息

主进程发送：

```ts
window.webContents.send('pocket:window-action', 'search')
```

preload 订阅并只转交业务参数：

```ts
onWindowAction: (callback) => {
  const listener = (
    _event: Electron.IpcRendererEvent,
    action: WindowAction
  ): void => callback(action)

  ipcRenderer.on('pocket:window-action', listener)
  return () => ipcRenderer.removeListener('pocket:window-action', listener)
}
```

这段是 `api` 对象里的方法节选。不要把 Electron 的原始 `event` 继续传给页面。

React 侧需要先订阅再握手，并在组件卸载时取消订阅：

```tsx
useEffect(() => {
  const api = window.api
  if (!api) return

  const unsubscribe = api.onWindowAction((action) => {
    if (action === 'settings') navigate('/settings')
    else searchRef.current?.focus()
  })

  // 项目中还通过 unwrap 与 toast 处理失败。
  void api.windowReady()
  return unsubscribe
}, [navigate])
```

`navigate`、`searchRef` 来自页面已有上下文。这里简化了浮层保护和错误提示，只用于说明订阅顺序。

React 开发模式可能反复执行 effect 的建立与清理；如果不取消监听，表现可能是一次事件触发多次回调。

## 5. 第五步：打开原生目录选择框

核心 API：`dialog.showOpenDialog()`。

项目节选：

```ts
const selection = await withNativeDialog(() =>
  dialog.showOpenDialog(window, {
    title: '选择命令的工作目录',
    buttonLabel: '选择此目录',
    properties: ['openDirectory']
  })
)

if (selection.canceled) return null
const cwd = await realpath(selection.filePaths[0])
```

第一个参数是所属原生窗口。传入窗口后，系统对话框与该窗口建立关系；不是在 React DOM 中插入一个弹窗。

| 参数或结果 | 含义 |
| --- | --- |
| `properties: ['openDirectory']` | 选择目录 |
| `properties: ['openFile']` | 选择文件 |
| `multiSelections` | 可选属性，允许多选；项目未用于执行目录 |
| `filters` | 文件类型筛选，例如 JSON |
| `canceled` | 用户是否取消 |
| `filePaths` | 返回的路径数组 |

文件类型筛选只是选择体验，不能替代内容校验。用户取消是正常分支，不应该作为“程序错误”提示。

`realpath()` 来自 Node.js，解析真实路径。它帮助后续比较实际目录，但不能把文件系统变成不会变化的快照。

## 6. 第六步：目录授权与二次确认

渲染进程能调用执行 API，不代表主进程应该接受它随意提供的任何路径。本项目把目录选择结果暂存在主进程：

```ts
const grants = new Map<string, { cwd: string; cmd: string; expires: number }>()

// 用户在系统选择框选好目录后记录。
grants.set(id, {
  cwd,
  cmd: command.cmd,
  expires: Date.now() + 5 * 60 * 1000
})
```

页面收到 `{ command, cwd }` 后展示二次确认对话框。用户确认时调用：

```ts
// 只提交命令 ID 和目录，不传新拼接出来的命令文本。
await window.api.executeCommand(command.id, cwd)
```

主进程会重新读取命令，并验证授权：

```ts
const grant = grants.get(id)
const command = data.commands.find((item) => item.id === id)

// 取出后立即消费，防止同一授权被反复使用。
grants.delete(id)

if (
  !grant ||
  grant.cwd !== cwd ||
  grant.cmd !== command?.cmd ||
  grant.expires < Date.now()
) {
  throw new Error('目录选择已失效或命令已修改，请重新选择目录并确认')
}
```

这样能处理“确认框打开后命令被修改”“页面传了另一个目录”“拿很久以前的选择结果执行”等情况。保存、删除命令和导入数据时还会清理相关授权。

二次确认是正常界面的用户交互；主进程的记录证明目录曾被选择、模板未改变，不是对页面点击行为的密码学证明，也不能消除当前页面被控制时的所有风险。

## 7. 第七步：执行规则为什么必须在主进程

`executable: true` 表示用户允许这条命令尝试执行；真正能否执行，还要通过主进程的固定白名单。

项目只允许首个程序名精确等于：

```ts
const EXECUTABLE_WHITELIST = new Set(['git', 'npm', 'pnpm', 'node'])
```

不是 `cmd.startsWith('git')`。否则 `git-other-tool` 也可能被误判。

执行接口不能写成：

```ts
// 反例：不要给渲染层一个可以提交任意命令文本的执行接口。
executeCommand(commandTextFromPage, directoryFromPage)
```

真实流程是主进程根据 ID 查询自己保存的模板，再解析它。用户录入模板和用户点击执行是两条不同业务路径：保存可以接受复制用的任意文本，执行必须重新验证。

### 7.1 为什么不能用 split(' ')

例如：

```text
git commit -m "修复快捷键隐藏逻辑"
```

引号内带空格的内容应作为一个参数。项目使用 `shell-quote` 解析，再拒绝不支持的 shell 操作。核心节选：

```ts
import { parse } from 'shell-quote'

if (!command.trim() || /[\r\n\0`$]/.test(command)) {
  throw new Error('仅支持单条命令，不允许换行、变量替换或 shell 代码')
}

const tokens = parse(command)
if (tokens.some((token) => typeof token !== 'string')) {
  throw new Error('不允许管道、重定向、注释或组合命令')
}

const [file, ...args] = tokens as string[]
if (!EXECUTABLE_WHITELIST.has(file)) {
  throw new Error('命令已拦截：仅允许 git / npm / pnpm / node 开头的指令')
}
```

上面的类型收窄建立在前面的运行时检查之上。完整 `parseExecutableCommand()` 还逐字符检查引号、反斜杠转义是否闭合；学习时不要把节选当成完整解析器替换项目原函数。

项目规则比较保守，例如含 `$` 的文本即使在某些引用方式下可作为字面量，也会被拒绝。复制命令不受这条执行限制影响。

| 模板 | 当前执行策略 |
| --- | --- |
| `git status` | 允许继续执行校验 |
| `npm i` | 允许继续执行校验 |
| `pnpm i` | 允许继续执行校验 |
| `node script.js` | 允许继续执行校验 |
| `git status && npm i` | 拒绝组合命令 |
| `git status > out.txt` | 拒绝重定向 |
| `echo hello` | 不在白名单 |
| `/usr/bin/git status` | 首个程序名不是固定白名单项 |

## 8. 第八步：用 spawn 启动程序

主进程使用 Node.js `child_process`，不是 Electron 专属命令执行 API。

一个可以单独理解的固定命令示例：

```ts
import { spawn } from 'node:child_process'

const child = spawn('git', ['status', '--short'], {
  cwd: '/你的项目目录',
  shell: false,
  windowsHide: true,
  stdio: ['ignore', 'pipe', 'pipe']
})
```

| 参数 | 含义 |
| --- | --- |
| 第一个参数 | 要启动的可执行程序 |
| 第二个参数 | 独立的参数数组，不是 shell 字符串 |
| `cwd` | 子进程工作目录 |
| `shell: false` | 不自动通过系统 shell 解释命令字符串 |
| `windowsHide: true` | Windows 下避免额外控制台窗口闪现 |
| `stdio[0] = 'ignore'` | 不提供交互式标准输入 |
| `stdio[1/2] = 'pipe'` | 捕获标准输出与标准错误 |

不要通过拼接 `cd 某路径 && 某命令` 设置目录。`cwd` 就是为这个用途设计的，包含空格的目录也不需要自己拼 shell 引号。

项目实际先 `findExecutable()` 找到程序绝对路径，再执行：

```ts
const child = spawn(executable.file, [...executable.prefix, ...parsed.args], {
  cwd,
  shell: false,
  windowsHide: true,
  stdio: ['ignore', 'pipe', 'pipe']
})
```

### 8.1 为什么终端能运行，桌面应用却找不到 npm

图形界面启动的应用继承的 `PATH` 可能不同于交互式终端。终端配置文件里加载的版本管理器，不一定自动出现在 Electron 环境中。

当前 `findExecutable()`：

1. 读取主进程 `process.env.PATH`。
2. 只遍历绝对路径目录。
3. 检查可执行文件并解析真实路径。
4. 找不到时提示安装或配置 PATH。

当前代码没有完整实现各种 Node 版本管理器的环境恢复。不要把“终端安装过 Node”直接等同于“从 Finder 启动也一定找到”。

### 8.2 Windows 的 npm.cmd 问题

Windows 上 npm、pnpm 入口可能是 `.cmd`，不能简单套用所有 Unix 可执行文件的调用方式。

项目遇到这类入口时尝试找到对应的 JS CLI 文件，再用 Node 启动：

```text
node.exe + npm-cli.js + 用户模板参数
```

这避免了为了兼容 `.cmd` 就全局开启 `shell: true`。当前查找方式依赖常见安装目录布局，不代表已经适配所有 pnpm、Corepack 或版本管理器的安装形式。

### 8.3 白名单的实际边界

这里的白名单限制直接启动的程序，并拒绝 shell 拼接；它不是操作系统沙箱。

`node` 能运行脚本，`npm` 安装可能触发生命周期脚本，Git 操作可能触发 hook。项目面向用户自己保存、理解并确认的开发命令。不能据此宣称允许列表里的所有参数或目标目录都“绝对安全”。

当前也不是交互式终端：需要密码、输入确认、REPL 的命令可能无法按终端方式交互。初始模板 `node` 仅表示启动 Node；要执行实际文件，应保存 `node script.js` 等明确模板。

## 9. 第九步：实时接收 stdout 和 stderr

项目监听子进程输出流：

```ts
child.stdout?.setEncoding('utf8').on('data', (text: string) => {
  output('stdout', text)
})

child.stderr?.setEncoding('utf8').on('data', (text: string) => {
  output('stderr', text)
})
```

`setEncoding('utf8')` 让回调得到字符串，并由流解码处理跨数据块的 UTF-8 字符。一次 `data` 不是固定一行，可能包含半行或多行，因此界面应按片段追加，不要假设每次都是完整日志行。

业务事件类型：

```ts
export interface ExecutionEvent {
  runId: string
  type: 'stdout' | 'stderr' | 'exit'
  text: string
  code?: number | null
}
```

`runId` 用于区分不同执行。主进程发送：

```ts
const send = (event: Omit<ExecutionEvent, 'runId'>): void => {
  if (!window.isDestroyed()) {
    window.webContents.send('pocket:execution', { ...event, runId })
  }
}
```

输出前调用 `stripVTControlCharacters()` 去掉终端控制字符，再以文本展示。它不是通用 HTML 消毒器；日志不要作为任意 HTML 插入页面。

页面需要**先订阅，再调用 execute**，因为短命令可能非常快，日志甚至会先于 `executeCommand()` 的 Promise 返回抵达。当前 `executionStore` 对尚未收到初始 runId 的阶段做了处理。

## 10. 第十步：结束、取消与资源上限

```ts
child.once('error', (error) => {
  send({ type: 'stderr', text: error.message })
  finish(-1)
})

child.once('close', (code) => finish(code))
```

`error` 处理启动失败等错误；`close` 表示相关标准流已关闭，用来收尾日志更合适。项目用 `finished` 标志防止两条路径重复收尾。

退出码 `0` 通常表示程序成功，非零通常表示失败；被信号终止时 code 可能是 `null`。不要只看到 stderr 有内容就判定失败，一些工具会把进度信息写入 stderr。

当前限制：

| 规则 | 实现 |
| --- | --- |
| 日志输出上限 | 累计 2 MB 后不再转发后续日志，并发出提示 |
| 执行时间 | 超过 10 分钟调用 `child.kill()` 请求停止 |
| 并行数量 | 主进程最多 3 个；当前页面交互一次管理一个运行任务 |
| 用户取消 | 根据 runId 找到 ChildProcess，调用 `kill()` |
| 应用退出 | 遍历记录的 ChildProcess，请求结束 |

`kill()` 是终止请求，不是“已确认所有子孙进程全部消失”。当前实现没有完整的跨平台进程树回收机制；npm 启动的后台服务等仍需要另外设计。

## 11. 第十一步：在哪里保存用户数据

项目用：

```ts
const repository = new Repository(
  join(app.getPath('userData'), 'pocket-data.json')
)
await repository.initialize()
```

`app.getPath('userData')` 让 Electron 提供当前用户、当前应用的数据目录，避免硬编码某台机器的 `/Users/名字/...`。实际路径以运行时返回值为准。

不要把可变数据写入打包后的 `app.asar` 或安装目录。应用更新、权限限制、只读安装位置都可能影响它们。

### 11.1 桌面数据和 Zustand persist 的关系

当前项目的数据流是：

```text
主进程 pocket-data.json：桌面应用的数据真源
  ↓ 启动时 loadData
Zustand：页面内存状态
  ↓ persist
localStorage：页面缓存
```

桌面启动时，主进程数据会同步到页面 store。保存操作通过 preload 请求主进程写盘，不应该只更新 localStorage 就告诉用户“桌面数据保存完成”。

浏览器预览没有 `window.api`，只能走前端预览能力，不能真正选择原生目录并启动本地程序。

### 11.2 首次启动与损坏文件要区分

`Repository.initialize()` 的规则是：

- 文件不存在，即 `ENOENT`：用初始数据创建文件。
- 文件存在但 JSON 或 schema 不合法：报错，保留原文件。
- 文件合法：加载已有数据。

不能把所有读取错误都当成“首次启动”，否则一个暂时损坏的文件可能被默认命令覆盖。

默认自定义命令有 `npm i`、`pnpm i`、`node`。清空命令后会持久化空数组；下次启动文件仍然存在，不会再次自动塞回默认命令。

## 12. 第十二步：为什么写文件还需要队列

用户可能快速收藏、编辑、删除。如果多个写入同时从旧状态开始，后完成的操作可能覆盖前面的变更。

项目用 Promise 队列串行执行：

```ts
private queue: Promise<unknown> = Promise.resolve()

async update(transform: (current: BackupData) => BackupData): Promise<BackupData> {
  const operation = this.queue.then(async () => {
    // 在轮到当前写入时再读取最新状态。
    const next = backupSchema.parse(transform(this.snapshot()))
    await mkdir(dirname(this.file), { recursive: true })
    await writeFile(`${this.file}.tmp`, JSON.stringify(next, null, 2), { mode: 0o600 })
    await rename(`${this.file}.tmp`, this.file)
    this.data = next
    return this.snapshot()
  })

  // 队列链吸收失败，让后续操作还能继续排队。
  this.queue = operation.catch(() => undefined)

  // 当前调用者仍然收到原始失败，不会误报成功。
  return operation
}
```

这段来自 `Repository` 类；`this.file` 是文件路径，`snapshot()` 用 `structuredClone()` 返回副本，避免外部直接修改内部数据。

先写同目录临时文件再 `rename()`，减少正式文件出现半截 JSON 的机会。只有落盘成功，才发布新的内存状态。它不是带 `fsync` 的完整断电持久性保证，也不能解决所有跨进程竞争。

`mode: 0o600` 表达用户私有文件权限，在支持 Unix 权限的系统上生效；不能把它理解成跨平台的加密。

## 13. 第十三步：导出备份

```ts
const selection = await withNativeDialog(() =>
  dialog.showSaveDialog(window, {
    title: '导出命令备份',
    defaultPath: 'jyt-pocket-backup.json',
    filters: [{ name: 'JSON 备份', extensions: ['json'] }]
  })
)

if (selection.canceled || !selection.filePath) return false

await writeFile(selection.filePath, JSON.stringify(repository.snapshot(), null, 2), {
  mode: 0o600
})
return true
```

`showSaveDialog()` 负责选保存位置，**不会替你写文件**。实际写入由 Node.js `writeFile()` 完成。

备份包含版本、命令、分组和设置，不只是命令字符串列表。版本字段用于识别数据格式，为未来迁移留出空间。

## 14. 第十四步：导入备份

核心顺序：

```text
选 JSON 文件
  → 检查文件体积
  → 读取文本
  → JSON.parse
  → Zod 校验结构及关联关系
  → 替换持久化数据
  → 更新页面 store
```

项目节选：

```ts
if ((await stat(file)).size > 10 * 1024 * 1024) {
  throw new Error('备份文件不能超过 10 MB')
}

let backup: unknown
try {
  backup = JSON.parse(await readFile(file, 'utf8'))
} catch {
  throw new Error('文件不是有效的 JSON 备份')
}

const result = backupSchema.safeParse(backup)
if (!result.success) {
  throw new Error('备份格式不正确，当前数据未改变')
}

grants.clear()
return repository.update(() => result.data)
```

`JSON.parse()` 成功只表示语法合法，不表示符合应用的数据结构。项目还校验版本、字段、数量上限、ID 去重、内置分组和命令分组引用等。

页面应在导入和清空前提供明确确认。主进程仍然负责实际校验与写入；不能把前端表单验证当成唯一防线。

## 15. 第十五步：置顶、主题、复制分别归谁

置顶是真正的原生窗口能力：

```ts
handle('pocket:always-on-top', (input) => {
  window.setAlwaysOnTop(z.boolean().parse(input))
})
```

项目的 `AppSetting` 当前只持久化 `theme`；置顶是窗口运行时状态，不能把它说成已经保存为重启后默认配置。

页面明暗主题由 CSS 变量、Zustand 设置与系统主题监听配合。`nativeTheme` 是 Electron 可用于原生主题的 API，但当前页面主题不需要为了切 CSS 而绕主进程一圈。

复制命令当前使用浏览器的 `navigator.clipboard.writeText()`。Electron 也有 `clipboard` 模块，但项目并没有为了这项功能新增主进程剪贴板 IPC；阅读时要区分“平台能做”和“项目实际用了”。

页面 CSP、禁用新窗口、拒绝整页导航与 preload 窄接口共同约束运行边界。当前 CSP 的样式策略含 `unsafe-inline`，不能描述成“所有内联内容都被完全禁止”。

## 16. 一次执行的完整回看

```text
保存模板：表单 → preload → 主进程 schema → Repository 写盘
执行准备：commandId → 查模板 → executable 与白名单检查
选择目录：系统对话框 → realpath → 主进程短期授权
确认执行：页面展示模板和目录 → 只传 ID、cwd
开始运行：再查模板与授权 → PATH 查找 → spawn(shell: false)
持续日志：stdout/stderr → runId 消息 → 页面追加文本
结束处理：close/error → 清定时器与进程记录 → 推送 exit
```

对应文件是 `ipc.ts`、`command-policy.ts`、`repository.ts`、`preload/index.ts` 和 `executionStore.ts`。把这些文件按调用链打开，就能从按钮一路追踪到操作系统进程。
