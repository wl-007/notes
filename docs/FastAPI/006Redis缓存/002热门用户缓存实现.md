# 生命周期、Redis 封装与热门用户缓存

对应提交：`c8e7394`（2026-11-09，使用 Redis）。

```bash
curl "http://127.0.0.1:8801/apiCommon/sys/user/popular?date=2026-11-13" \
  -H "Authorization: Bearer $TOKEN"
```

当前接口按日期区分缓存键，但未按日期筛选用户。某日期第一次请求时，从数据库读取**当前最新创建的前 N 个未删除用户**，写入该日期缓存。

```text
sys:user:popular:2026-11-13
```

它是按日期分桶的最新用户快照，不是历史创建用户查询，也不是按访问量计算的热度排行榜。

## 生命周期管理连接

项目启动时调用 `connect_redis()`，把客户端放在 `app.state.redis`；退出时关闭 Redis 客户端和数据库引擎：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.redis = await connect_redis() if settings.REDIS_ENABLE else None
    try:
        yield
    finally:
        await close_redis(app.state.redis)
        if settings.SQL_DB_ENABLE:
            await close_db()
```

`yield` 前是启动阶段，后是退出阶段。关闭客户端连接不会删除 Redis 数据，也不会停止 Redis 服务器；后端进程被强制杀死时，finally 也不保证执行。

每个后端 worker 有自己的客户端与连接池，访问的 Redis 服务可以相同。不要在每个请求里重新创建客户端。

## 连接配置与可选依赖

`Redis.from_url()` 使用：

```python
encoding="utf-8"
decode_responses=True
health_check_interval=20
socket_timeout=settings.REDIS_SOCKET_TIMEOUT
socket_connect_timeout=settings.REDIS_SOCKET_TIMEOUT
```

项目默认超时为 3 秒，启动后执行一次 `PING`。`decode_responses=True` 使常规文本返回为字符串，而不是字节。

| 配置 | 作用 |
| --- | --- |
| `REDIS_ENABLE` | 是否尝试启动 Redis 客户端 |
| `REDIS_URL` | 非空时优先使用完整 URI |
| `REDIS_HOST/PORT/DB_NAME` | 分项连接参数 |
| `REDIS_USER/PASSWORD` | 认证参数，实际凭据由环境管理 |
| `POPULAR_USER_LIMIT` | 默认 10，允许 1 到 100 |
| `POPULAR_USER_CACHE_TTL` | 默认 86400 秒 |

逻辑库编号不提供强安全隔离，也不表示各库拥有独立持久化文件。托管或集群部署的逻辑库支持还要看具体服务。

请求通过依赖读取共享客户端：

```python
async def redis_getter(request: Request) -> Redis | None:
    return getattr(request.app.state, "redis", None)
```

## RedisCURD 封装负责什么

类名在源码中拼为 `RedisCURD`，文章保留该标识，避免复制代码时导入失败。

| 方法 | 返回约定 | 故障处理 |
| --- | --- | --- |
| `get(key)` | 字符串或 None | 记录日志，返回 None |
| `get_json(key)` | JSON 解析结果 | 无效 JSON 返回 None |
| `set(key, value, expire)` | bool | 非字符串先 JSON 编码，设置 EX |
| `delete(*keys)` | bool | 无参数直接成功，异常返回 False |
| `ttl(key)` | int | 异常返回 -1 |

这里吞掉异常是“缓存为可选加速层”的业务选择。若用于余额、必须送达的任务等关键数据，不能直接照搬这种把失败降级为成功路径的设计。

`ttl()` 把故障也映射为 -1，调用方无法仅靠此值区分“没有过期时间”与“查询 TTL 失败”。

## Cache Aside：先缓存，未命中再回源

当前实现步骤：

1. 解析 `date`，缺省使用服务器本地日期。
2. 按日期构造缓存键，读取 JSON。
3. 如果是列表，逐项用 `UserOutSchema.model_validate()` 验证。
4. 缓存有效则返回 `cache_hit=True`。
5. 缓存缺失或无效，调用 `UserCRUD.list_latest()` 查询。
6. 按 `created_at DESC, id DESC` 取前 N 条，转换为输出 Schema。
7. 写回 JSON，并返回 `cache_hit=False`。

持久化恢复不能代替第三步：文件可恢复，不意味着缓存结构符合当前代码的 Schema。接口字段变化时可以考虑版本化键前缀，避免旧结构混用。

## TTL 的实际算法

当天的 TTL：

```python
max(60, min(
    settings.POPULAR_USER_CACHE_TTL,
    int((tomorrow - now).total_seconds()),
))
```

非当天日期使用配置 TTL，默认 86400 秒。

通常当天缓存会在接近本地次日零点时到期，但最小值为 60 秒，因此零点前最后一分钟写入的缓存可能跨日继续存活。日期在键中，所以次日默认请求会使用新的键。

这里用 `date.today()` 和无时区的 `datetime.now()`，依赖运行服务器时区；多实例时区不一致可能产生不同日期键。JWT 的 UTC 时间和接口返回的 `expires_at` 不意味着这部分自动也按 UTC 分桶。

## 如何理解响应中的缓存信息

```json
{
  "code": 1,
  "msg": "成功",
  "data": {
    "query_date": "2026-11-13",
    "items": [],
    "cache_key": "sys:user:popular:2026-11-13",
    "cache_hit": false,
    "expires_at": null
  }
}
```

- 首次回源即使写缓存成功，当前也返回 `cache_hit=false` 和 `expires_at=null`。
- 命中时，TTL 大于 0 才计算 UTC 的预计过期时间；TTL 为 0 或负数时仍返回 null。
- Redis 故障导致写入失败，接口仍可成功回源，不能从成功响应推断缓存已存储。
- 参数 `date` 支持合法日期，没有限制只能查询过去。历史或未来日期未命中时同样读取数据库当前数据。

## 数据变更后的失效

注册、修改或删除用户时，Service 删除**当天**的榜单键，下次请求重建。其他日期键不会同步失效，已有内容会保留到过期，可能包含变更前的昵称或后来已删除的用户。

因此其他日期也不能当作可靠的历史审计数据。如果需求是所有日期都立即反映用户变化，需要重新设计键与失效策略；如果需求是真实历史快照，则应使用专门的历史数据模型。

当前缓存删除发生在 Service 内，此时数据库事务尚未退出提交。并发读取可能在删除后、提交前回源，将旧数据重新写回。数据库事务和 Redis 删除也不是一个原子事务。

对一致性更敏感时，应评估提交后失效、版本键、事件驱动或 outbox 等方案，并定义允许的陈旧时间；不要把一次 DEL 描述成已经解决所有一致性问题。

## Redis 挂掉或恢复时

| 场景 | 当前行为 |
| --- | --- |
| 启动时连接失败 | 保存 None，后续请求直接查 MySQL |
| 启动时失败、之后 Redis 恢复 | 当前没有重新初始化调度，通常需要重启后端重新取得客户端 |
| 已有客户端、运行中 Redis 断开 | 读取失败返回 None，回源数据库 |
| 已有客户端、Redis 后来恢复 | 后续操作可能重新建立连接，不能认为失败中的请求自动无损重试 |
| MySQL 也不可用 | 缓存降级不能替代数据库可用性 |

`health_check_interval` 不是独立的无限后台重试任务。启动时根本没保存客户端，与已有客户端短暂断线，是两种不同情况。

Redis 是否能恢复键值取决于 [持久化配置](./001Redis基础与持久化.md)。当前仓库没有服务端持久化配置，不能从这个提交断言已开启 RDB 或 AOF。

## 缓存穿透、击穿和雪崩

| 问题 | 含义 | 常见处理思路 |
| --- | --- | --- |
| 穿透 | 大量请求查询不存在的数据，持续打到主库 | 合法性校验、短期空值缓存、适用时用布隆过滤器 |
| 击穿 | 热点键失效，大量并发请求同时重建 | 单次重建协调、互斥、逻辑过期配合后台刷新 |
| 雪崩 | 大批键同时失效或 Redis 故障，回源骤增 | TTL 抖动、预热、限流、熔断和容量预案 |

当前空榜单 `[]` 可以被缓存，但日期允许任意合法值，仍可能产生大量不同键。代码没有实现分布式重建锁、抖动、请求限流或回源并发控制。

使用锁时也要考虑锁的过期、持有者标识和安全释放；普通 `SETNX` 后无条件 DEL 不足以形成可靠锁。先定义允许的并发与一致性，再选择成熟方案。

拿有效令牌对同一日期连续请求，观察第一次回源和后续命中；用 Redis 只读命令核对：

```bash
redis-cli GET sys:user:popular:2026-11-13

```

示例使用本地默认端口，按实际认证配置调整；不要把密码直接写进可分享的命令。验证失效时，修改本人昵称后再查询当天；验证持久化时，单独使用上一章的练习实例。
