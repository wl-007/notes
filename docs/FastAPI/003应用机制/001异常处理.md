
## 先区分异常来源

| 类别 | 例子 | 调用方应该如何理解 |
| --- | --- | --- |
| 请求校验异常 | 字符串不能转换为整数 | 请求数据不符合声明 |
| 预期业务异常 | 用户不存在、用户名重复 | 请求被业务规则拒绝 |
| 认证与权限异常 | 未登录、操作他人账号 | 身份或操作范围不满足 |
| 框架 HTTP 异常 | 路由不存在、方法不支持 | HTTP 层无法完成请求 |
| 未预期异常 | 程序错误、未处理的外部服务故障 | 服务端需要定位问题 |

业务层抛出异常，HTTP 边界统一转换响应，比在每个路由写相同的 `try/except` 更容易保持一致。异常处理器不是自动修复机制；事务回滚、资源释放仍应由上下文管理器等负责。

## 自定义异常承载哪些信息

当前类的核心结构：

```python
from typing import Any


class CustomException(Exception):
    def __init__(
        self,
        msg: str = "系统异常",
        code: int = -1,
        status_code: int = 400,
        data: Any = None,
    ):
        super().__init__(msg)
        self.msg = msg
        self.code = code
        self.status_code = status_code
        self.data = data
```

它同时携带业务码和 HTTP 状态。比如系统用户重复注册：

```python
raise CustomException(
    msg="用户名已存在",
    code=RET.DATAEXIST.code,
    status_code=409,
)
```

早期示例模块有些调用只设置业务码，HTTP 状态仍使用默认 400；不能从 `code=404` 推断 HTTP 也是 404。

## 处理器如何注册

`main.create_app()` 调用 `register_exceptions()`，后者调用 `handle_exception(app)`。核心用法是：

```python
@app.exception_handler(CustomException)
async def custom_exception_handler(request, exc):
    return ErrorResponse(
        msg=exc.msg,
        code=exc.code,
        status_code=exc.status_code,
        data=exc.data,
    )
```

处理器匹配异常类型，返回真正的 Response。当前项目另有 `Exception` 和 FastAPI `HTTPException` 两个处理器。

`1718f4e` 修正了 HTTP 异常读取字段的方式，使用 `detail` 和 `status_code`，而不是自定义异常的 `msg/code`。

## 当前哪些错误仍不统一

| 异常 | 当前响应行为 |
| --- | --- |
| `CustomException` | `code/msg/data`，保留指定 HTTP 状态 |
| 直接抛出的 FastAPI `HTTPException` | 转成 `ErrorResponse`；业务码默认 0 |
| `RequestValidationError` | 保留默认 422 和 `detail` 结构 |
| Starlette 产生的普通 404 / 405 | 使用框架处理器，通常仍为 `detail` |
| 未预期 `Exception` | 500，消息为“服务器内部错误” |

FastAPI 的 `HTTPException` 继承 Starlette 的版本。当前注册的是子类处理器，不会反过来覆盖框架直接产生的基类异常。

此外，当前 HTTP 异常处理器未透传 `exc.headers`。如果异常携带 `WWW-Authenticate` 或 `Retry-After`，这些头部不会自动保留。参数校验、框架异常和异常头的完整统一属于后续改进方向，本文没有把它描述成已完成。

## 错误处理与事务

请求内抛出异常时，数据库 `yield` 依赖退出 `session.begin()`，触发回滚。不要捕获数据库错误后直接返回“成功”，否则事务依赖可能无法按预期感知失败。

捕获异常后转换业务异常时，可以使用 `raise ... from exc` 保留异常链。对外不暴露数据库连接串、SQL 参数和堆栈；对内仍需要记录足够的定位信息。

当前兜底处理器返回通用消息，但没有真正调用日志记录。虽然文件导入了 `traceback`，并不代表异常堆栈已经落入日志。

不依赖数据库的分支可以通过 `/getErr` 和错误参数演示验证：

