# 中间件与 CORS 跨域

对应提交：`9d821b7`（2026-10-09，新中间件与跨域配置）。

本地前端从 `http://localhost:5173` 请求 `http://127.0.0.1:8801` 时，协议即使相同，主机和端口仍然不同，所以是跨源请求。

## 中间件在请求链路中的位置

```text
请求 → 外层中间件 → 内层中间件 → 路由
响应 ← 外层中间件 ← 内层中间件 ← 路由
```

中间件适合统一处理请求和响应，例如跨域、压缩、请求 ID、访问日志。依赖注入更适合提供路由所需的用户、数据库会话等资源；异常处理器负责将异常转换成响应。

中间件也可以提前返回，不进入业务路由。CORS 预检就是典型例子。

## 浏览器为什么发送 OPTIONS

对于不满足简单请求条件的跨源请求，浏览器先发送预检：

```bash
curl -i -X OPTIONS \
  "http://127.0.0.1:8801/apiCommon/sys/user/me" \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: GET" \
  -H "Access-Control-Request-Headers: authorization"
```

预检询问允许的源、方法和头部，成功后浏览器才发送实际请求。携带 `Authorization`、使用 `application/json` 等情况通常会触发预检。

curl 用于观察服务端头部，不执行浏览器的跨域拦截。curl 成功而网页失败时，应检查预检、Origin 和响应头。

CORS 约束浏览器脚本读取跨源响应，不是用户认证、防爬或服务端接口访问控制。部分请求仍可能被发送，因此也不能把 CORS 当作完整的 CSRF 防护。

## 项目如何配置

```python
class CustomCORSMiddleware(CORSMiddleware):
    def __init__(self, app):
        super().__init__(
            app,
            allow_origins=settings.ALLOW_ORIGINS,
            allow_methods=settings.ALLOW_METHODS,
            allow_headers=settings.ALLOW_HEADERS,
            allow_credentials=settings.ALLOW_CREDENTIALS,
            expose_headers=settings.CORS_EXPOSE_HEADERS,
        )
```

| 配置 | 含义 |
| --- | --- |
| `allow_origins` | 允许访问的源列表 |
| `allow_methods` | 允许的请求方法 |
| `allow_headers` | 实际请求允许携带的头部 |
| `allow_credentials` | 是否允许凭据场景 |
| `expose_headers` | 浏览器 JS 可读取的额外响应头 |
| `max_age` | 预检结果的缓存秒数，项目未显式覆盖 |

项目默认 `ALLOW_ORIGINS=["*"]` 且 `ALLOW_CREDENTIALS=True`。学习时要认识到，带凭据的浏览器响应不能依靠 `Access-Control-Allow-Origin: *` 放行；实际使用 Cookie 等凭据时应明确列出源、方法和头部，避免依赖通配配置的边缘行为。

例如本地开发配置可以写成：

```dotenv
ALLOW_ORIGINS=["http://localhost:5173","http://127.0.0.1:5173"]
ALLOW_METHODS=["GET","POST","PUT","DELETE","OPTIONS"]
ALLOW_HEADERS=["Authorization","Content-Type"]
ALLOW_CREDENTIALS=true
```

这是建议配置示例，本次没有修改项目环境文件。`localhost` 和 `127.0.0.1` 是不同主机，不能只写其中一个却期待另一个自动匹配。

## Cookie 跨域还取决于什么

浏览器需要客户端启用凭据传输，例如 fetch 的 `credentials: "include"`；服务端需允许凭据并返回合适的具体源。同时 Cookie 自身仍受 Domain、Path、SameSite、Secure 等限制。

“跨源”和“跨站”不是同一个概念，SameSite 采用站点规则，不单纯按端口区分。设置了 CORS 不代表 Cookie 一定会被发送。

Bearer 登录通常由客户端显式设置 `Authorization`。当前系统用户采用这种方式，`/setCookie` 的演示 Cookie 不参与系统登录。

## 动态注册与执行顺序

`Settings.MIDDLEWARE_LIST` 返回中间件类的导入路径。注册时反向遍历：

```python
for middleware in settings.MIDDLEWARE_LIST[::-1]:
    if not middleware:
        continue
    middleware_class = import_module(middleware, desc="中间件")
    app.add_middleware(middleware_class)
```

由于后添加的用户中间件包在外侧，反向注册可以让配置列表的第一项成为这些用户中间件中的最外层。

动态导入工具先用 `rsplit(".", 1)` 分离模块路径与类名，再使用 `importlib.import_module()` 和 `getattr()` 取得类。它不负责自动发现所有中间件。

当前列表实际只有可选的 CORS 中间件。配置注释提到的请求日志、安全头、GZip、CorrelationId 尚未接入，不应当作已启用能力。

Starlette 自带的错误处理层还有自己的包裹关系。通过 `add_middleware()` 添加 CORS，不保证所有最外层生成的未处理 500 都带跨域头；若业务要求错误也能被跨域客户端读取，应验证该路径并考虑按官方方式包裹整个 ASGI 应用。
