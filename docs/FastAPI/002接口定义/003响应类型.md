# 响应模型与统一返回结构

对应提交：`de407fd`（2026-10-09，参数解析情况）。数据库与登录提交又引入了 ORM 输出和令牌响应。

当前系统用户注册成功时，HTTP 状态码是 `201`，JSON 中的业务码默认仍是 `1`：

```json
{
  "code": 1,
  "msg": "成功",
  "data": {
    "id": 1,
    "username": "alice",
    "nickname": "Alice",
    "is_active": true,
    "created_at": "2026-11-13T10:00:00",
    "updated_at": "2026-11-13T10:00:00"
  }
}
```

这是结构示例，ID 和时间以数据库实际值为准。

## response_model：校验和过滤输出

下面是可以独立运行的示例，不是当前项目接口：

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class UserIn(BaseModel):
    username: str
    password: str


class UserOut(BaseModel):
    username: str


@app.post("/users", response_model=UserOut)
async def create_user(user: UserIn):
    return user.model_dump()
```

传入 `{"username":"alice","password":"demo-password"}`，虽然返回字典中包含密码，最终输出只包含 `username`。`response_model` 同时影响 OpenAPI、返回值校验、序列化和字段过滤。这里显式返回字典，避免把两个不同 Pydantic 模型之间的对象转换当成默认保证；从对象属性读取时需配置 `from_attributes`。

输入不合法通常是 422；返回值不符合响应模型属于服务端实现问题，默认是 500。输出过滤不能代替密码哈希，数据库存储仍需单独设计。

旧笔记中的 `/test/user/createUser` 和 `/current/info` 属于早期演示，`94140a9` 后已由数据库 CRUD 路由替换，不再当作当前可调用接口。

## 泛型响应封装

项目定义了：

```python
from typing import Generic, TypeVar

from pydantic import BaseModel, Field

T = TypeVar("T")


class ResponseSchema(BaseModel, Generic[T]):
    code: int = Field(default=1, description="业务状态码")
    msg: str = Field(default="成功", description="响应消息")
    data: T | None = Field(default=None, description="响应数据")
```

路由使用具体的泛型参数，文档才能准确表达 `data`：

```python
@UserRouter.get("/me", response_model=ResponseSchema[UserOutSchema])
async def get_me(current_user: CurrentUser):
    return SuccessResponse(
        data=UserOutSchema.model_validate(current_user)
    )
```

`SuccessResponse` 继承 Pydantic 响应模型，负责填入 `data/msg/code`；它不是 `JSONResponse`。最终过滤仍由路由声明的 `ResponseSchema[UserOutSchema]` 完成。

## 从 ORM 转为输出模型

```python
from pydantic import BaseModel, ConfigDict


class UserOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    username: str
```

`model_validate(orm_object)` 从属性读取字段。只声明要公开的字段，避免把 `password_hash` 输出给客户端。模型必须在字段已加载且会话适当可用时转换，不能指望序列化阶段自动完成任意异步懒加载。

## HTTP 状态码和业务码各管什么

| 内容 | 位置 | 当前项目示例 |
| --- | --- | --- |
| HTTP 状态码 | HTTP 响应状态行 | 注册 201，未登录 401，越权 403，冲突 409 |
| 业务码 `code` | JSON 响应体 | 成功 1，重复用户名 4003，无效令牌 4504 |
| 消息 `msg` | JSON 响应体 | 面向调用方的说明 |
| 业务数据 `data` | JSON 响应体 | 用户对象、分页结果或 null |

`RET.CREATED.code == 201` 不会自动改变 HTTP 状态码。成功状态由路由 `status_code` 决定，错误状态由错误响应决定。

## 直接返回 Response 会怎样

项目的 `ErrorResponse` 继承 `JSONResponse`，在异常处理器中直接返回。此时 FastAPI 不再按路由的 `response_model` 转换内容，所以必须自行准备 JSON 可序列化数据。

项目通过 `jsonable_response_content()` 调用 `jsonable_encoder()`，将 `datetime/date/time` 等转换后再交给 `JSONResponse`。文件和流式响应同样属于直接返回 Response 的场景，不能套用 JSON 输出模型来理解。

| 返回方式 | 适用情形 |
| --- | --- |
| 字典 / Pydantic 模型 | 常规 JSON 接口，交给框架序列化 |
| `JSONResponse` | 自行控制状态、头部和 JSON 内容 |
| `FileResponse` | 下载已有文件 |
| `StreamingResponse` | 分块输出流；异步迭代器可用于异步数据源 |

`response.py` 导入了后两种类型，但当前文件上传路由只是占位，不能据此认为项目已实现下载或流式传输。

## 日期输出不是全局统一改写

`constant.py` 中定义了：

```python
DATE_DISPLAY_FMT = "%Y-%m-%d"
TIME_DISPLAY_FMT = "%H:%M:%S"
DATETIME_DISPLAY_FMT = "%Y-%m-%d %H:%M:%S"
```

这些格式用于错误响应辅助函数中的自定义编码路径。普通 Pydantic 响应没有配置全局日期序列化器，通常仍输出 ISO 风格日期时间。不能仅凭常量存在就认定所有成功响应都是空格分隔格式。

如果业务需要统一格式，应明确在输出模型中设计序列化规则，并决定时区；格式化字符串不能解决数据库和应用时区不一致。

## 当前封装的边界

登录接口返回标准的 `{"access_token":"...","token_type":"bearer"}`，刻意不包 `code/msg/data`，以便 Swagger OAuth2 登录使用。参数校验错误和部分框架错误也没有全部进入自定义封装，详见 [异常处理](../003应用机制/001异常处理.md)。
