# Docker 进阶

## 1. 进阶主要学什么

如果入门阶段解决的是“单个容器能跑起来”，那进阶阶段解决的通常是：

- 多容器项目怎么管理
- 镜像怎么构建得更合理
- 开发和生产环境怎么区分
- 怎么排查容器问题
- 怎么减少镜像体积和构建时间

## 2. 为什么项目里几乎都会用 Docker Compose

Docker 官方文档把 Compose 定义为：

> 用来定义和运行多容器应用的工具。

它的核心价值是：

- 用一个 YAML 文件管理整个应用栈
- 服务、网络、卷都能统一描述
- 一条命令就能把整套服务拉起来

## 3. 一个最小 Compose 示例

```yaml
services:
  web:
    build: .
    ports:
      - "3000:3000"
    depends_on:
      - redis

  redis:
    image: redis:7
```

启动：

```bash
docker compose up
```

后台启动：

```bash
docker compose up -d
```

停止并删除容器：

```bash
docker compose down
```

## 4. Compose 常见配置项

### `services`

定义应用里的服务，比如：

- `web`
- `api`
- `db`
- `redis`

### `build`

指定用当前项目的 Dockerfile 构建镜像。

### `image`

直接使用已有镜像。

### `ports`

端口映射。

### `volumes`

挂载数据卷或本地目录。

### `depends_on`

声明服务启动依赖关系。

注意它主要解决“启动顺序”问题，不等于“服务已经完全可用”。

### `environment`

传环境变量。

## 5. 开发环境常见 Compose 写法

本地开发时，很多项目会把源码目录挂进容器：

```yaml
services:
  app:
    build: .
    ports:
      - "5173:5173"
    volumes:
      - .:/app
    command: npm run dev
```

这样改代码时，容器里通常能即时看到变化。

这个模式适合开发，不一定适合生产。

## 6. 多阶段构建

多阶段构建是 Docker 里非常重要的优化手段。

它的核心目的是：

- 构建阶段用完整工具链
- 运行阶段只保留真正需要的产物

例如前端项目：

```dockerfile
FROM node:20-alpine AS builder

WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 80
```

这样做的好处：

- 最终镜像更小
- 不把构建依赖带进运行环境
- 更适合生产部署

## 7. 构建优化的几个高频点

### 先复制依赖清单，再安装依赖

典型写法：

```dockerfile
COPY package*.json ./
RUN npm install
COPY . .
```

原因：

如果源码改了但依赖没改，可以更好利用构建缓存。

### 使用 `.dockerignore`

`.dockerignore` 用来排除不该进入构建上下文的文件。

例如：

```gitignore
node_modules
dist
.git
.DS_Store
```

这样可以：

- 减少构建上下文体积
- 提高构建速度
- 避免把无关文件打进镜像

## 8. 日志、排障和查看状态

项目里最常用的不是部署命令，而是排障命令。

查看 Compose 服务状态：

```bash
docker compose ps
```

查看日志：

```bash
docker compose logs
```

只看某个服务：

```bash
docker compose logs web
```

实时追日志：

```bash
docker compose logs -f
```

进入服务容器：

```bash
docker compose exec web sh
```

查看容器详细信息：

```bash
docker inspect 容器名
```

## 9. 数据库容器要特别注意什么

数据库类服务最常见的问题不是“起不来”，而是“数据没持久化”。

比如 MySQL：

```yaml
services:
  mysql:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: 123456
    volumes:
      - mysql-data:/var/lib/mysql

volumes:
  mysql-data:
```

这里的关键点是：

- 数据目录要挂卷
- 环境变量要明确
- 账号密码不要直接硬编码到公开仓库

## 10. 生产环境里要注意什么

### 不要默认把开发命令搬到生产

开发环境可能是：

```bash
npm run dev
```

生产环境通常不应该这样跑。

### 不要把源码整个挂进去

开发时常见：

```yaml
volumes:
  - .:/app
```

生产里通常更偏向：

- 构建好镜像
- 直接跑镜像
- 减少对宿主机目录的依赖

### 不要把敏感信息写死

比如：

- 数据库密码
- API Key
- 私有仓库凭据

这些应该通过环境变量或更安全的配置方式传入。

## 11. Compose 适合什么，不适合什么

### 适合

- 本地开发环境
- 测试环境
- 小中型多容器项目
- 快速搭建依赖服务

### 不适合

- 大规模集群编排
- 更复杂的弹性伸缩和调度场景

这时一般会走 Kubernetes 一类方案。

## 12. 一套实用工作流

如果你做的是一个常见 Web 项目，可以按这个节奏落地：

1. 写应用 Dockerfile
2. 写 `compose.yaml`
3. 把数据库、缓存、应用一起编排
4. 用 volume 保存数据库数据
5. 用 `.dockerignore` 优化构建
6. 用多阶段构建缩小生产镜像
7. 用 `docker compose logs` 和 `exec` 做排障

## 13. 一组常用命令

```bash
# 启动全部服务
docker compose up

# 后台启动
docker compose up -d

# 停止并清理
docker compose down

# 查看服务状态
docker compose ps

# 查看日志
docker compose logs

# 跟随日志
docker compose logs -f

# 重建并启动
docker compose up --build

# 进入容器
docker compose exec web sh
```

## 14. 本篇小结

进阶阶段最重要的不是记更多命令，而是理解下面这些事情：

- Compose 是多容器项目的主工作流
- `.dockerignore` 和构建缓存会明显影响构建效率
- 多阶段构建会明显改善生产镜像质量
- volume、logs、exec、inspect 是排障高频点
- 开发环境和生产环境的 Docker 用法不能完全照搬
